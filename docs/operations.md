# Operations

`docker compose up -d --build` builds the production client/server and starts Caddy plus one Node process. `data/` is a read-only bind mount so manually generated artifacts can be replaced without rebuilding the image. After `bun run city:generate`, restart `game` to load the file. Never regenerate during startup. Production debug is explicitly disabled in the compose environment.

Default local HTTPS is localhost:8443. Caddy's local CA root lives in its persistent data volume; copy it with `docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./local-root.crt` and trust it using your operating system certificate manager for local browser testing. Do not commit certificates/private keys. Public DNS/domain mode uses ACME certificates; set DOMAIN plus HTTP_PORT=80 and HTTPS_PORT=443 before starting compose. Both ports must reach Caddy. WebSocket upgrades and Host/Origin are preserved by reverse_proxy.

The VibePod preview gateway rewrites Host to the local server address. WebSocket origin checks use its overwritten `X-Forwarded-Host` only for peers at `127.0.0.1`, `::1`, or IPv4-mapped `127.0.0.1`. Other peers must preserve Host; their forwarded headers are ignored. A local reverse proxy must overwrite `X-Forwarded-Host` with the requested public host, or strip it when preserving Host. Cross-origin and malformed origins remain rejected. The preview gateway's password screen or HTTP 401 requires signing in to the gateway, independently of game reconnects.

`docker compose logs -f game caddy` includes startup failures and structured HTTPS request logs. `/health` exposes aggregate CPU/runtime diagnostics; it contains no reconnect tokens or player names. Monitor p95 tick time against 33.33 ms, catch-up drops, RSS growth, outgoing bytes, and reconnect failures. Periodic container health checks report failure; restart policies recover a crashed process, while an unhealthy-but-running process needs an external monitor/operator restart. No claim of automatic failover is made.

Shutdown releases connections with "Server restarting". Browsers retry; a restarted process creates a fresh dynamic world, and old reconnect tokens expire with it. The immutable city artifact is persisted; dynamic players, inventory, traffic damage and clock are intentionally reset. An in-process disconnect keeps its player for 15 seconds, releases inputs and vehicle ownership, and deploys a parachute for an airborne aircraft occupant. Empty aircraft retain momentum and fall/crash. One replica hosts one city; do not load-balance clients over independent copies of the process.

The local deployment acceptance test checks HTTPS content, WSS joining, production cheat gating, artifact delivery, health, and reconnect after `docker compose restart game`. A public-domain launch remains an operator action requiring a domain/host; no public deployment is implied by local container validation.

Health includes `traffic` counters for persistent jam groups/cars, cumulative horns and wreck replacements, and pending replacements. A growing replacement queue usually means clear road sites are unavailable; the server retries without forcing overlaps. Traffic diagnostics and the queue reset on process restart. See [traffic lifecycle](traffic.md).

## Cluster deployment

On each push to `main`, CI runs formatting, type checks, unit tests and the production build, then publishes `ghcr.io/michidk/afterhours` for AMD64 and ARM64. Tags are `sha-<full commit>` and `main`; the image job summary records the immutable manifest digest. Browser movement checks run separately and remain visible when software rendering cannot sustain their speed gates. Their failure does not establish whether the cluster server meets the tick budget.

The image includes the built client assets and saved city artifact. Its single Node process serves HTTP, map chunks and WebSockets on port 5173 with production debug disabled. Deploy it through `apps/afterhours/` in the sibling k8s repository at `https://afterhours.k8s.lohr.dev`. That repository owns the digest pin, ingress, resource reservation and rollout. To promote another build, update its tagged digest, run `just verify`, and push its `main` branch. A single-replica Recreate deployment prevents two independent city processes from receiving players during rollout; updates disconnect players and reset transient state.

The first cluster rollout uses gameplay/image commit `5fbdfe3`, pinned by manifest digest, on `work.lohr.dev` with a 200m CPU request, no CPU limit, a 512 Mi memory request and 1 Gi limit. The initial 300m reservation left a pre-upgrade hook unschedulable; 200m leaves transient-job headroom. The deployment workflow explicitly waits for the game Deployment to become ready. Local container checks passed with a read-only filesystem; public HTTPS/WSS acceptance confirmed client assets, the saved artifact/chunks, disabled debug RPC and in-process reconnects. Loading text was visually checked headlessly at 960px after the shared T3 automation host disconnected.

Deployment does not establish a performance pass. One 20.8-second observation with no connected players averaged 24.8 ticks/sec, with p95 68–77 ms across five overlapping rolling windows of 600 ticks. An initial sample after the resource adjustment still reported p95 67.5 ms. These are observations on the production ARM worker, not a controlled comparison with the preview or native GPU measurements. The simulation's 33.33 ms target remains unmet; server profiling and client measurements remain in `todo.md`. Raw local evidence is `/tmp/afterhours-cluster-health.json`.
