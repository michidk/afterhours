# Browser playtesting

Run `bun run dev` and open two desktop browser tabs on the same server. Give them distinct names/colours. In development, `window.afterhours` is a read-only diagnostics view of the received/predicted state, pending input count, corrections, ping estimate, particle/skid counts, renderer, FPS, and the last 600 frames' p95 duration. It cannot change server outcomes. Production omits these diagnostics and disables F1 cheats by default.

1. Verify that the loading stage downloads `/city`, becomes ready, and joins without shader errors. Compare the city received by both clients; static layout and signal phases should agree.
2. Walk diagonally, sprint, stop, and slide along a building. Verify movement in the observer tab and exclusive driver ownership. Keep another player near the spawn to check that newly joined players use separate safe positions.
3. Enter the sedan, sport, and van. Accelerate, steer, use Space to drift, then release it. Observe fading tyre trails on both clients, wheel steering, correct speed/health HUD, and collision response. Use ramps at (3.5,91) or (-124.5,-37).
4. Damage a vehicle using F1 while aboard, exit and move away. Confirm smoke/flames, a six-second countdown, explosion, nearby damage, occupant release, wreck appearance, and cleanup after 20 seconds. F1 heal cancels fire before explosion for repeatable setup.
5. Enter the Sparrow/Atlas. Observe automatic climb, flight over roofs/trees, and the altitude HUD. F must immediately release the player and deploy a visible parachute on both clients. Steer with WASD, land on a street/roof, and confirm the canopy disappears and walking resumes. Empty aircraft retain momentum and fall/crash with damage, fire, and eventual explosion on severe impacts. Disconnect a pilot and confirm the aircraft follows the same abandoned behavior.
6. At Paloma Airfield (160,-160), accelerate the plane along the marked runway. Hold E above 19 m/s, fly, and press F to parachute out while the empty plane continues and crashes. Also test normal stall/landing with Q, ground braking, and grounded exit without a parachute. Walls and street traffic still collide with grounded aircraft.
7. Obtain a pistol/SMG/bat from a pad or F1. Mouse aim and left click/J attack; 1–4 equip; R reload; G drop. Confirm held models, ammo/tracers/audio, wall-blocked shots, nearer-item F prompt, exclusive pickup by the other client, four-slot cap, and 120-second dropped-item despawn. Supply pads refill 20 seconds after collection.
8. Let traffic and pedestrians run through several signal cycles. Observe destination changes, turns, queues, crosswalk waits, panic, knockdowns/recovery and jam reversal. Use day/night tools to check readability and M to mute audio.
9. Chat from both tabs. Close a socket/tab and reconnect within 15 seconds; stale controls must stop. Restart the server and confirm a fresh dynamic world using the saved artifact. Replace the artifact with a different seed and restart: the browser reloads the new geometry.
10. Board the same vehicle from multiple clients. Verify capacities, distinct seat assignments, role/occupancy HUD, rejection when full, passenger controls having no effect, smooth shared movement, independent passenger exits, driver disconnect with passengers aboard, vacant-seat reuse, and explosion damage to everyone aboard. Helicopters allow a one-second boarding pause; pilot movement skips it. Passenger parachute exit must preserve pilot ownership and flight.

## Hardware client observations (further profiling waived)

The server uses CPU only. The **client** needs a GPU. A user-supplied RTX 4070 / Chrome 152 / 1588x1271 sample measured ~165 FPS and rolling p95 35.2 ms. It confirms hardware rendering but misses the 33.3 ms target. The rolling 600-frame view is only a short window at high refresh rates.

The optimized full-minute retest returned p95 9.4 ms, update p95 0.6 ms, render p95 8 ms, and UI p95 0.9 ms. It also returned `valid:false` with a 15.94-second maximum frame interval. With nonzero samples, that profiler version marks a run invalid only after a tab-hidden visibility event; therefore this result is encouraging but does not satisfy the uninterrupted hardware acceptance check. Its reported 96.49 FPS used summed frame intervals; the corrected profiler divides samples by the full wall-clock duration and reports `invalidReasons` plus `hiddenSeconds`.

The user waived further hardware profiling as an acceptance requirement. Preserve both reports as observations, without treating the invalid retest as a verified performance pass. The optional `window.afterhours.profile(60)` diagnostic remains available and reports elapsed-time FPS, p95/max frame times, per-stage timings, renderer, viewport, pixel ratio, and tab visibility.

## Other repeatable checks

`bun run test` covers simulation/transport invariants, including jittered input delivery, stale sequence rejection, snapshot recovery, malformed messages, reconnect tokens, bounded lag compensation, and offline city loading. WebSockets deliver packets reliably/in order; tests exercise burst/jitter/control loss rather than claim datagram packet-loss handling.

`bun run bench:load` runs 16 moving WebSocket clients for 30 seconds, writes `docs/load-test.json`, and fails if p95 CPU ticks exceed 33.33 ms or catch-up drops occur. `LOAD_SECONDS` changes the run length. This is a local CPU capacity test, not a WAN soak test or GPU test.

`bun run test:deployment --restart` checks the local Docker/Caddy HTTPS/WSS stack, artifact identity, cheat gating, session restoration and world reset after a container restart. Its local CA exception applies only to localhost; public HTTPS must pass normal certificate validation.
